# タイピング練習アプリ データベース（DB）仕様書

本仕様書は、タイピング練習アプリで使用するデータの構造と、保存ロジックを定義したものです。将来的な拡張や詳細なデータ分析、予期せぬ不具合への対応を見据え、最も重要な「学籍番号の永続性」と「成績データの改ざん防止」を徹底しています。

---

## 1. データベースの全体構造（テーブル関連図）

アプリのデータを以下の**7つのテーブル**で管理します。「主キー」と「外部キー」を用いたリレーション構造により、データの重複や矛盾を防いでいます。

※ **注記**: SQLiteはテーブル定義時に管理テーブル（`sqlite_sequence` など）を自動生成するため、実際のデータベース内には8つ以上のテーブルが表示される場合がありますが、本設計の対象は7テーブルのみです。SQLiteの内部テーブルは設計対象外であり、削除・修正の対象ではありません。

| テーブル名 (英語) | 日本語訳 | 役割 |
| :--- | :--- | :--- |
| **users** | ユーザー | ユーザー（生徒）の基本情報を管理 |
| **stages** | ステージ | 学習の大分類カテゴリ（章）を定義 |
| **levels** | サブステージ | ステージに属する個別の練習問題セット（節）と「AIへの出題指示」を管理 |
| **keyboards** | キーボード | ユーザーごとの利用キーボードを登録 |
| **keys** | キー設定 | キーボード内における「キーと指の割り当て」を定義 |
| **logs** | プレイ記録 | 1問ごとのプレイ結果・履歴（※上書き不可・蓄積型） |
| **assignments** | 課題 | 教員が出す課題（レベル・締め切り・回数・正確率の条件） |

| **sort_order** | 表示順 | INTEGER(整数) | NOT NULL<br>DEFAULT 0 | | ステージ内での表示順。<br>※裏側の管理番号(`id`)に関係なく、ここに指定した数字の順番で画面に表示されます。問題の順序変更に対応。 |

| **description**| 説明文 | TEXT(長文) | NULL許容 | | この問題セットのクリア条件やコツなど。 |
| **prompt** | 生成プロンプト | TEXT(長文) | NOT NULL | | AIに問題を自動生成させるための指示文。 |
| **is_active** | 表示フラグ | INTEGER(整数) | NOT NULL<br>DEFAULT 1 | **インデックス** | `0` で非表示（論理削除）。非表示のレベルは学生の画面に出ず、出題もされません。過去の記録はそのまま残ります。 |

### ⑥ プレイ記録 (`logs`)
1問（1単語）ごとのプレイ結果を保存します。
> 💡 **ポイント**: このテーブルには `stage_id` がありませんが、`level_id` を遡ることで「どのステージか」を特定できます。
> また、`keyboard_id` に加えて **`user_id` も直接保持**しています。これにより「ユーザーが過去のキーボード設定を削除しても成績データが安全に残る」という設計になっています。

| カラム名 (英語) | 日本語訳 | 型 | 制約 | キー | 説明 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **id** | ログID | INTEGER(整数) | NOT NULL<br>AUTOINCREMENT | **主キー** | 履歴番号。 |
| **session_id** | プレイ単位ID | TEXT(文字) | NOT NULL | **インデックス** | 「1回のプレイ」全体をまとめるための合言葉（例:`abc-123`）。これがないとプレイの流れが分からなくなります。 |
| **user_id** | ユーザーID | TEXT(文字) | NOT NULL | **外部キー** | 【親: users】誰のプレイ記録か。 |
| **level_id** | レベルID | INTEGER(整数) | NOT NULL | **外部キー** | 【親: levels】どの問題を解いたか。 |
| **keyboard_id**| キーボードID | INTEGER(整数) | NULL許容 | **外部キー** | 【親: keyboards】どのキーボードで解いたか（※専用設定がない場合はNULLを許容します）。 |
| **question_num**| 出題番号 | INTEGER(整数) | NOT NULL | | そのレベルの中で「何問目の出題だったか」を記録。<br>※これがないと、1回のプレイ(`session_id`)の流れが分からなくなります。 |
| **target** | 出題文 | TEXT(長文) | NOT NULL | | 本来打とうとした問題のテキスト（AI生成結果）。 |
| **typed** | 実入力文 | TEXT(長文) | NOT NULL | | ユーザーが実際に打ち込んでしまったテキスト（ミスを含む）。<br>※Enter を押した時点で入力欄に残っている文字列を保存します（Backspace で消した文字は含みません）。 |
| **start_time** | 開始日時 | TEXT(日時) | NOT NULL | | その問題の練習をスタートした日時（問題が画面に表示された時点）。<br>※形式は ISO8601・UTC・ミリ秒まで（例: `2026-10-16T01:23:45.678Z`）。 |
| **end_time** | 終了日時 | TEXT(日時) | NOT NULL | | その問題の練習が完了した日時（Enter を押した時点。形式は start_time と同じ）。（開始との差分が1問の所要時間） |

> 📊 **データ記録の設計（1問＝1レコード）**
> 1回の出題（1単語）につき、必ず1行のデータを追加します。
> 
> 🎮 **【重要】アプリの動きと保存タイミングの連動**
> 画面に出た問題（例：`jjjj`）を打ち終わり、生徒が**「エンターキー」を押して次の問題へ進んだ瞬間**に、その問題の「出題文(target)」「実際に打ち込んだ全文字(typed)」「開始と終了の日時」がデータベースに自動保存されます。
> 
> これにより、「第何問目で間違えたか」「どの単語に何秒かかったか」といった細かい分析がデータベース上で簡単に検索できるようになります。
> スコア・WPM・正確率などはデータベースには保存せず、このテーブルの `target`、`typed`、および `start_time`、`end_time` から動的に計算します（計算処理はアプリの画面とサーバーで共通のものを使います）。

### ⑦ 課題 (`assignments`)
教員が出す課題です。「いつまでに、どのレベルを、何回、どの正確率で」を保存します。達成したかは保存せず、`logs` から毎回計算します（🅲 と同じ考え方）。
| カラム名 (英語) | 日本語訳 | 型 | 制約 | キー | 説明 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **id** | 課題ID | INTEGER(整数) | NOT NULL<br>AUTOINCREMENT | **主キー** | 管理番号。 |
| **title** | 課題名 | TEXT(文字) | NOT NULL | | 「人差し指の練習を3回」など。 |
| **level_id** | レベルID | INTEGER(整数) | NOT NULL | **外部キー** | 【親: levels】どのレベルの課題か。 |
| **due_at** | 締め切り | TEXT(日時) | NOT NULL | | ISO8601・UTC・ミリ秒（`logs` の日時と同じ形式）。画面では日本時間の日付で入力し、その日の終わり（23:59:59.999）を保存します。 |
| **required_plays** | 必要な回数 | INTEGER(整数) | NOT NULL<br>DEFAULT 1<br>CHECK 1以上 | | 条件を満たすプレイが何回あれば達成か。 |
| **min_accuracy** | 正確率の条件 | REAL(小数) | NULL許容<br>CHECK 0より大きく1以下 | | 数えるプレイの正確率の下限。`NULL` ならレベルの `pass_accuracy` を使い、それもなければ10問解いたプレイを数えます。 |
| **created_at** | 作成日時 | TEXT(日時) | NOT NULL | | 課題を出した日時。これより前のプレイは数えません。 |
| **is_active** | 有効フラグ | INTEGER(整数) | NOT NULL<br>DEFAULT 1 | **インデックス** | `0` で削除（論理削除）。学生の画面から消えます。 |

> 💡 **達成の数え方**: 課題を出した日時（`created_at`）から締め切り（`due_at`）までに、そのレベルで、10問すべて解き、正確率の条件を満たしたプレイ（`session_id` ごと）の数が `required_plays` 以上なら達成です。

## 3. データベース運用方針（自由な拡張と設計の安全性）

本システムは運用開始後の追加や変更に、シンプルに対応できるよう構成されています。

### 🅰️ 問題の追加と表示順の管理

システム内で「問題（ステージやレベル）」は自由に追加できます。

ステージおよびレベルの表示順は `sort_order` カラムで管理します。

不要になったステージ・レベルは、`is_active` を `0` にして非表示にします（論理削除）。練習の記録（`logs`）が指しているものは、記録を守るため完全には削除できません（外部キーで拒否されます）。記録のないものは完全に削除できます。非表示のステージ・レベルは学生の画面に出ず、出題もされません。過去の記録の分析には、そのまま使われます。

非表示のステージに属するレベルは、レベル自体が表示でも学生の画面には出ません。

### 🅱️ 記録の「改ざん防止」と「永続的トラッキング」
教育データとして、「昨日の記録が消えた」「上書きされて分からなくなった」という事態は致命的です。
* **対策**: `logs` テーブルは「挿入（Insert）」のみを許可する蓄積型の設計としています。上書きは決して行われないため、万が一生徒の成績が急に変わってしまった場合も「何月何日のどの問題で何が起きたのか」が完全に追跡できます。
* **仕組み**: `logs` テーブルにはトリガー `logs_no_update`（上書き禁止）と `logs_no_delete`（削除禁止）を設定しており、UPDATE・DELETE を実行するとデータベースがエラーで拒否します。

### 🅲 スコアリングルールの変更（関心の分離）
運用途中で「やっぱりスコアの計算式を変えたい」「WPM以外にも新しい独自指標を導入したい」という教員からの要望が出る可能性があります。
* **対策**: データベースにはスコア・WPM・正確率などの「計算結果」を一切保存しません。すべて `target`・`typed`・`start_time`・`end_time` から動的に計算します（計算処理はアプリの画面とサーバーで共通のもの。教員向けの集計や CSV 出力はサーバーで計算します）。これにより「過去何年分ものデータも新しいルールで『再計算』できる」という究極の柔軟性を実現しました。

### 🅳 AI連携とキャッシュ戦略（コスト・速度最適化）
`levels` テーブルの `prompt` を使ってAI（OpenAIやGemini等）に問題を自動生成させる際、生徒がプレイするたびに毎回AIを呼び出すと、APIの利用料金が非常に高くなってしまいます。
* **対策**: 
  1. APIキーの漏洩を防ぐため、AIとの通信は必ずフロントエンド（画面）ではなく**バックエンド（サーバー側）**で行います。
  2. 一度AIが生成した問題のリストは、サーバー側で一定期間（例：1時間〜1日）**キャッシュ（一時保存）**して使い回す設計とします。
  これにより、「APIコストの極小化」と「待ち時間ゼロのサクサク動くプレイ環境」を両立させることができます。

### 🅴 外部キーの有効化
SQLite では、外部キーのチェックは接続ごとに `PRAGMA foreign_keys = ON;` を実行したときだけ働きます（データベースファイルには保存されません）。そのため、データベースに接続するプログラムは、接続のたびに必ずこの命令を実行します。

## 修正歴
* **SQLiteの仕様に合わせたデータ型修正**
  * `boolean(真偽値)` を `INTEGER(整数)` に変更し、デフォルト値を `1`、無効値を `0` に変更（SQLiteにはBOOLEAN型が存在せずINTEGERで代用されるため）。
  * `varchar(文字)` を `TEXT(文字)` に変更（SQLiteにはVARCHAR型がなく、文字列はすべてTEXTとして扱われるため）。
  * `datetime(日時)` を `TEXT(日時)` に変更（SQLiteにはDATETIME型がなく、一般的にTEXTのISO8601形式などで保存されるため）。
* **2026-10-02: 定義と実際のデータベースの一致**
  * `users.id` に NOT NULL を明示（SQLite では TEXT 型の主キーに NULL が入ってしまうため）。
  * `logs` に上書き・削除を禁止するトリガーを追加（🅱️の方針をデータベース側でも保証するため）。
  * 表の型表記を実際の定義（`INTEGER`・`TEXT`・`AUTOINCREMENT`）に統一。
  * 外部キーの有効化（🅴）とインデックス一覧（🅵）を追記。
* **2026-10-16: 記録の形式を明記**
  * `typed` は Enter を押した時点の入力欄の文字列、`start_time` / `end_time` は ISO8601・UTC・ミリ秒までと明記（既存のデモデータ 5 件はタイムゾーン表記なしの秒単位。アプリは UTC として扱う）。
  * 🅲 のスコアの計算場所を実装に合わせて修正（「フロントエンドで計算」→「画面とサーバーで共通の計算処理」）。DB の構造は変更なし。
* **2026-10-16: ステージ・レベルを非表示にできるようにした**
  * `stages`・`levels` に `is_active`（`INTEGER NOT NULL DEFAULT 1`）とインデックスを追加。既存のステージ・レベルはすべて `1`（表示）。
  * 理由: 練習の記録があるレベルは完全に削除できない（`logs` は削除禁止、外部キーで参照されている）ため、不要になったものを画面から外す手段が必要になった（本人の判断）。2026-07 の Issue #14 で `stages`・`levels` の `is_active` は一度削除しており、今回それを戻す形になる。
  * `logs` のトリガー（上書き・削除の禁止）と既存のデータは変更なし。
* **2026-10-23: 合格の目安と課題を追加**（本人の指示: 管理側から「正確率95%以上で合格」などを設定でき、設定なしで自由に練習もできること。いつまでに何を何回・正確率や合格などの課題を出せること）
  * `levels` に `pass_accuracy`（REAL、NULL許容）を追加。`NULL` は目安なし（自由に練習）。
